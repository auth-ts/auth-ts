```ts
import { createAuthClient } from "@auth-ts/client"

export const authClient = createAuthClient()
```

Construction performs no network request and touches no storage, so importing the
module is free and safe during server-side rendering. Everything reconciles on
the first read.

## The two reads

`getToken()` returns a valid access token from its cache, or `null` when nobody
is signed in. Approaching expiry it hands back the cached one and refreshes
behind you; only a token too close to expiry to outlive the request it would be
used for makes you wait. Concurrent callers share a single refresh, so a page
mounting ten components makes one round-trip and they all see the same token.

Hand it to your PostgREST client as its access token: Neon's `fetchWithToken`
takes exactly this shape and raises its own error on `null`, so a query made
while signed out fails as a data-plane error rather than an auth one. It also
means "is anyone signed in" is a question you can ask without a `try`.

`getUser()` returns the signed-in user, or `null`, and **always reads the
server**. There is no cache behind it on purpose: a name or avatar changed in
another tab, on another device, or by anything other than this client has to
arrive somehow, and deciding when to ask again is yours to make. When it has to
refresh anyway — a page load, a fresh tab — the user comes off the refresh, so a
cold read costs one request rather than two.

`null` means the server said the session is gone, and the stored token is dropped
with it. Every other failure throws — a 502 from a proxy is not a statement about
whether anyone is signed in.

`getSession()` returns the session this browser is on. Its `id` is how a device
list tells which entry is this device.

The client keeps no user state at all. No mirror, no `localStorage`, no cross-tab
listener. Caching, persistence, retry, and refetch-on-focus are what a query
library already does well, and doing them here would only give you two sources of
truth to keep in step.

## Where tokens come from

Two places, both a body. `GET /token` exchanges the refresh cookie for one, and
a sign-in returns one with the user it signed in — verification code, guest,
account switch, and the sign-out that promotes a parked account. Nothing arrives
in a response header, so there is nothing for a framework's response plumbing to
lose and nothing for CORS to expose.

Every authenticated method calls `getToken()` before it sends, because the server
authenticates from the token and refuses anything else. That is invisible from
the outside: the token is served from cache, so a page that already holds a live
one costs no extra round trip, and ten methods called at once share one refresh
if they need it.

`getToken()` serves from that cache. Approaching expiry it hands back the cached
token and refreshes behind you; only a token too close to expiry to outlive the
request it would be used for makes you wait.

A 401 is retried once with a fresh token before it is believed. Refresh-ahead
covers the ordinary case, but a key rotated between mint and use, or a device
clock far enough off that the window never fired, both look like a refusal on a
token the client had every reason to trust. A second refusal is the session
genuinely being gone.

**Your data plane gets the same treatment, but you have to write it.** PostgREST
talks to Neon directly and never passes through your server, so an expired token
there is a hard 401 with nothing to rescue it:

```ts
const token = await authClient.getToken()
if (!token) return // Signed out; there is nothing to ask the data plane for.

let response = await fetch(url, { headers: { authorization: `Bearer ${token}` } })

if (response.status === 401) {
  authClient.clearToken()
  const fresh = await authClient.getToken()
  response = await fetch(url, { headers: { authorization: `Bearer ${fresh}` } })
}
```

Once, never in a loop: if the second attempt is also refused, the session is
genuinely gone.

The client's own methods are the other side of this. They need a credential
rather than an answer, so a call made without a session throws
`unauthenticated` — `getUser()` and `signOut()` excepted, which resolve to
`null` because "nobody" is a real answer to what they ask.

## React

Nothing bridges into your cache, so the query is the only source of truth:

```tsx
export function useUser() {
  return useQuery({
    queryKey: ["session"],
    queryFn: authClient.getUser,
    refetchOnWindowFocus: true,
    staleTime: 60_000
  })
}
```

`data` is the user, or `null`. `getSession()`'s `id` is how a device list tells
which entry is this device — the list does not carry a flag saying so.

Anything that changes who is signed in has to invalidate that key, because
nothing else will:

```tsx
await authClient.verifyCode({ email, code })
await refetch()          // or queryClient.invalidateQueries(...)

await authClient.signOut()
queryClient.clear()
```

Persistence across a cold load, if you want it, is your query client's persister
— the same one you would use for any other data.

## Native

A browser holds the refresh cookie itself and never shows it to JavaScript. A
native app has no such jar, so the client can be one: pass `cookieStorage` and it
keeps whatever the server sets in the storage you give it, sends it back as the
`Cookie` header on every auth request, and drops what the server clears. The
server is none the wiser, and the refresh token still travels nowhere but the
cookie header.

```ts
import * as SecureStore from "expo-secure-store"

export const authClient = createAuthClient({
  baseURL: "https://app.example.com",
  cookieStorage: {
    getItem: (key) => SecureStore.getItemAsync(key),
    setItem: (key, value) => SecureStore.setItemAsync(key, value),
    removeItem: (key) => SecureStore.deleteItemAsync(key)
  }
})
```

The shape is the web `Storage` interface, so a store that already has
`getItem`/`setItem`/`removeItem` passes straight through. Use one the platform
protects — the keychain or keystore — because what lands in it is the session.

Everything else is unchanged: `getToken()` still serves the JWT from memory for
your data client, and the app never touches the cookie. OAuth is the exception
for now — `signIn` and `connect` navigate the page, which a native app cannot do;
deep-link flows are on the roadmap.

## Errors

Every failure is an `AuthError` carrying a stable `code`. Switch on the code,
never on the message — messages are localized and free to change.

```ts
import { isAuthError } from "@auth-ts/client"

try {
  await authClient.sendCode({ email })
} catch (error) {
  if (isAuthError(error) && error.code === "cooldown") {
    // error.retryAfter is in seconds. Render a countdown; "try again later"
    // with no number is the least useful message in software.
  }
}
```

A dropped connection raises `AuthNetworkError` instead, because only one of those
two should clear local state.

## Retrying a data request

On a 401 from your data API, drop the token, fetch a new one, and retry **once**.
Never loop: if the second attempt is refused too, the session is genuinely gone.

```ts
if (response.status === 401) {
  authClient.clearToken()
  response = await send()
}
```
