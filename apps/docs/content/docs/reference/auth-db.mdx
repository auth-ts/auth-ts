This interface is the product. You write these functions against your own tables,
and in exchange the library never owns your schema, your migrations, or your data.

Two conventions run through it. `upsert*` takes the entity; `get*`, `list*`, and
`delete*` take a `where` query. And upserts are deliberate rather than split into
create-and-update: the create-or-merge race is delegated to your store, where
`ON CONFLICT`, `MERGE`, or `$setOnInsert` settles it atomically, instead of being
relocated into this library as a read-then-write on every sign-in.

Callbacks never receive request headers. Header-dependent session resolution is a
spoofable authentication bypass, and non-HTTP callers — tests, migrations, the
in-memory fixture — drive this contract directly. For multi-tenancy, close over
the tenant when you construct the server.

## The rules that are easy to get wrong

These are not enforced by types, so they are worth reading once:

- **`upsertUser` has three shapes.** An identifier with no `id` looks up and
  merges. No identifier at all always inserts — that is guest creation. An `id`
  targets exactly that row, which is guest conversion and profile updates.
- **`type` and `additionalFields` are insert-only** on the identifier-keyed path.
  Merging them would demote an administrator on their next sign-in, and let any
  sign-in body rewrite profile columns.
- **`deleteUser` must remove the user's sessions.** A cascade does this for free.
  An account that keeps a live refresh token is still a working login.
- **Every `delete*` returns what it deleted** — `DELETE … RETURNING *`,
  `findOneAndDelete`, `OUTPUT deleted.*` — or `null` when nothing matched. Core
  relies on that: it is how a revoke answers 404 without a second query, and how
  a magic code becomes usable exactly once.
- **`deleteMagicCode` must match on `codeHash` when it is given**, in one
  statement. Two requests can both read the row and both pass the HMAC check;
  the database lets only one of them delete it. That single conditional delete
  is the whole one-time guarantee — it is exactly what Better Auth's
  `consumeOne`, Auth.js's `useVerificationToken`, and InstantDB's `consume!` do.
- **`upsertRateLimit` is an atomic increment, and the store owns the count.**
  Insert with `count = 1` if the key is absent or its window has passed;
  otherwise add one and keep the existing `resetAt` — in one statement
  (`ON CONFLICT … DO UPDATE SET count = CASE …`). Core never reads the counter
  first: a read-then-write lets ten parallel requests each see the same value
  and register as one, which is exactly the burst a limiter exists to stop.
- **`deleteSession({ id, userId })` must filter on both columns**, so that
  revoking another user's session id matches nothing.
- **`deleteExpired` takes no arguments.** Expired means expired now, and your
  database already knows the time — `expiresAt < now()` avoids any skew between
  your application server and Postgres.

## Testing your implementation

The in-memory implementation the library's own test suite runs against is public:

```ts
import { createMemoryDb } from "@auth-ts/server/testing"

const db = createMemoryDb()
```

Testing against it means testing against the same semantics the library verifies
itself with, rather than a simplified mock that agrees with your assumptions.
