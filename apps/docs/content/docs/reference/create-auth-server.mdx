```ts
import { createAuthServer } from "@auth-ts/server"

export const authServer = createAuthServer({
  db: {
    /* four functions — see the AuthDB reference */
  },
  email: { sendCode: async ({ email, code }) => {} }
})
```

Construction is synchronous and does no input/output, so it is cheap to memoize
one instance per tenant. Everything that can be wrong with a configuration throws
here — a missing key, no sign-in method, a reserved field name — with the
offending option named, rather than surfacing on the first user's sign-in.

Two words are used deliberately. **Options** are what you pass: the partial,
human-written `AuthServerOptions` below. **Config** is what resolving them
produces: `AuthServerConfig`, with every default applied and every value
validated, exposed as `authServer.config`. When options cannot be resolved into
a config, construction throws an `AuthConfigError`.

## Generating ids

Unset by default, and unset is usually right: rows go to your store without an
`id` and your own column default fills it — `uuidv7()`, a `$defaultFn`, an
identity column, whatever the table already does. `insert` hands the stored row
back, so the library reads the id it was given rather than assuming one.

```ts
createAuthServer({
  db: authDB,
  generateId: (table) => `${table}_${crypto.randomUUID()}`
})
```

Set it when ids are the application's to mint: a store with no default of its
own, a prefixed id, or an id you need to know before the write. It is called
once per inserted row, awaited, with the table name, and the result becomes that
row's `id`.

## Cleanup

There is no `cleanup` option. Sweeping expired rows is a query, so it lives on
[`AuthDB.cleanup`](/docs/reference/auth-db) — implement it and the library runs
it for you, at most once a minute after a request that could have written
something; leave it out and the schedule is yours. Something has to run it:
the `attempts` table gains a row per rate-limited request.

## What you get back

The same endpoints, three ways, all derived from one registry so they cannot
disagree:

```ts
// 1. Call it directly from your own backend. No HTTP round-trip to yourself.
const session = await authServer.getToken({ headers }) // null when nobody is

// 2. One catch-all handler, mounted once.
authServer.handler(request)

// 3. Individual handlers, if you prefer explicit routes.
authServer.handlers.sendCode(request)
```

Plus the JWT-plane functions:

- `verifyToken(token)` — verifies locally against the public key. No database, no
  network. Returns `null` for any failure.
- `signToken(claims)` — mints anything, with no session check. This is the
  private key with a function signature; never expose it through a route.
- `decodeToken(token)` — **unverified**, synchronous, for logging and triage.
  Never authorize with it.
- `getToken({ headers })` — exchanges the refresh cookie for an access token,
  and returns the user with it, or `null` when nobody is signed in. The one
  function that reads the cookie.
- `getSession({ headers })` — the session the caller is acting from. One
  read, no user lookup: the one the token's `sid` names.

### The token is the credential

Every authenticated endpoint takes `{ headers?, token? }` and authenticates from
the access token alone: a token passed directly, then an `Authorization: Bearer`
header, then a 401. There is no cookie fallback.

`GET /token` is the exception, and the only one. It reads the refresh cookie,
slides the session, signs a token, and answers with `{ token, user }`. Nothing
else touches a session at all.

It answers `null` rather than throwing when there is no session — a visitor
nobody is signed in as is the ordinary case on a public page, not a failure —
so a loader branches instead of catching:

```ts
// Server-side rendering: buy a token once, then spend it.
const session = await authServer.getToken({ headers })
if (!session) return { user: null }

const sessions = await authServer.getSessions({ token: session.token })
```

That shape is the point. A loader that called four endpoints with `{ headers }`
under a cookie fallback would slide the session four times, read the user four
times, and sign four tokens it then threw away. One exchange plus four token
reads costs one session write and no signatures.

Sign-ins hand back a token in the body alongside the user — verification code,
guest, account switch, and the sign-out that promotes a parked account — so
signing in and the first render cost one round trip between them rather than a
sign-in followed by a refresh. Nothing crosses in a response header any more,
which is also why there is nothing for CORS to expose.

`GET /connect/:provider` is the one authenticated route that still accepts the
cookie, because `location.assign` is a top-level navigation and cannot carry an
`Authorization` header. It prefers the token when one is there.

The cost of trusting a token is revocation latency: a session revoked elsewhere
keeps working until that token expires, `jwt.ttl` at the outside. That is the
same bound your database already lives with, since it authorizes on the token
too.

Every refusal is logged at `debug` with a `reason` of `missing`, `expired`, or
`invalid`. Counting them is worth doing: a client refreshes ahead of expiry, so a
healthy deployment refuses about never — a rate above that is a client that has
stopped refreshing, showing up as a graph rather than as user reports.

## Additional fields

`user.additionalFields` declares the extra columns on your users table that
sign-up may set and `POST /user` may edit — a name → type map, and the source
of truth for types as well as validation. Declare a field and every user this
server returns carries it, typed:

```ts
const authServer = createAuthServer({
  db,
  user: { additionalFields: { plan: "string", seats: "number" } }
})

const user = await authServer.getUser({ token })
user.plan // string | null | undefined
```

Optional and nullable on the way out, because nothing guarantees a row has set
them; optional and never null on the way in, because core only writes a value
that validated against its declared type. Requests that send an undeclared key
or the wrong primitive are rejected with `invalidField`, and declared fields are
applied on insert only — signing in cannot overwrite an existing profile. Typing
your `AuthDB` against the same schema is covered in [AuthDB](/docs/reference/auth-db#typing-your-implementation).

## Client IP

`ipAddress` decides how the client's address is read from proxy headers — the
per-IP rate-limit key, and the `ipAddress` stored on each session. It needs no
configuration where the platform overwrites `x-forwarded-for`; a chain of two or
more entries is ambiguous until you say what your topology is, and until then no
address is derived from it. See [Security](/docs/security#deploying) for what
each form is worth.

```ts
createAuthServer({
  // Cloudflare, Akamai: a header the edge controls and a client cannot append to.
  ipAddress: { headers: ["cf-connecting-ip"] }
})

createAuthServer({
  // Behind proxies you run: their count, or their addresses.
  ipAddress: { trustedProxies: 1 }
})
```

During development — `NODE_ENV=development` — a request with no forwarded header
reports `127.0.0.1` rather than nothing, so per-IP limits are testable on the one
machine where you want to try them. Nothing is invented in production.

## Durations

Every duration uses one format — `"10m"`, `"30d"`, `"60s"` — and one parser, so
`jwt.ttl` and a rate-limit window cannot disagree about what `"1h"` means. Months
are unsupported because their length is ambiguous.
