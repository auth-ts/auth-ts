Every item here has a test. Several exist because the failure mode is a full
account takeover rather than a bug.

## Verification codes

Six symbols by default, from an alphabet of thirty-two — uppercase letters and
digits without the four that get misread — drawn from a CSPRNG one masked byte
at a time, with the overflow rejected rather than reduced: never
`Math.random()`, and never a plain modulo, which biases the range and therefore
shrinks it. `verificationCode` switches to digits for phones that autofill
one-time codes, and sets the length.

Stored under **scrypt** at 16 MiB (`N=2^14, r=8, p=1`, a fresh 16-byte salt,
parameters carried in the string), never as a fast hash. A short code has few
enough values that a SHA-256 of it falls to a GPU in seconds; at scrypt's cost
a leaked table takes far longer to reverse than its codes live, and nothing
else has to stay secret for that to hold. This is the one place the server
reaches for `node:crypto`, which Node, Bun, Deno and Workers all provide; a
runtime with only Web Crypto can run everything here except the code flow.

**An email address is validated by the book's rules and never modified.** At
most 100 characters, exactly one `@`, lowercase letters, digits and `. _ + -`
before it, a dotted domain of lowercase letters, digits, `.`, `-` and `_`
after — the author's `verifyAccountIdentifierEmailAddressPattern`, ported.
Anything else is **400 `invalidEmailAddress`**, including capitals and
surrounding spaces: what the user typed is what is stored, sent to and shown, and
quietly lowercasing it is the thing the book warns against. An address a
provider hands over is machine data rather than input, so it is lowercased as
GoTrue does and then held to the same rules; one that fails counts as no
verified address, so an existing account still signs in by its provider
identity and a first sign-in is refused.

**Every code is bound to the client that asked for it.** A send hands back an
attempt token — as an `HttpOnly` cookie scoped to the auth mount, and in the
body for callers with no cookie jar — and stores its hash beside the code. A
verify reads exactly one row: the address, the purpose, and that attempt. A
stranger requesting a code for your address gets a code of their own; they
cannot replace yours, spend yours, or guess at yours, so there is no limit on
how many codes an address may have in flight and nothing an attacker can do to
keep you from starting a sign-in.

What is limited is **guessing, per address, from anyone**: five guesses in
five minutes by default, and the sixth is refused before it is compared. That
is the one budget an attacker holds against an account, and at six symbols from
thirty-two it takes on the order of a thousand years of nonstop guessing —
emailing the target every ten minutes to keep a live code — to reach even
odds. Under that attack the real user's guess may be refused for the rest of
the window; their code is never touched. No slow hashing — the ten-minute
lifetime and the guess budget do that job, and bcrypt here would only slow down
honest sign-ins.

Purposes are checked on verify, so a sign-in code can never confirm an
identity, and the two carry separate attempt cookies so requesting one does not
orphan the other.

`/user/verify/send-code` is the one call that puts an identity code in flight,
and it needs the caller's own bearer token. Revoking a device and deleting the
account never send anything themselves — without a verification they refuse
outright, with no side effect, so retrying cannot fire a storm of email.

A code whose delivery fails is rolled back rather than left live, so a sender
outage leaves nothing bound to the token the person is about to present.

## Rate limiting

On by default, and the book's design: a token bucket per key, five tokens and
one back every minute for guesses, keyed the way the author's app keys its
buckets — on the address for a sign-in code, on the user for an identity code,
on the address for sends (five, then one every half hour). The one bucket keyed
on the client's IP is guest sign-in, because a guest has nothing else to key
on; its default is GoTrue's thirty an hour.

Each bucket is one row in `rateLimits`: `tokenCount` and `lastRefilledAt`.
Taking a token is a read and an update that names both values it read, so two
requests that read the same bucket cannot both take the last token — the second
finds the row changed, writes nothing, and reads again; after three lost races
it is refused, which is the safe direction. No atomic increment is asked of your
store, and no failed attempts are tracked, as the book says they need not be. A
refused request writes nothing; a bucket that has refilled is the same as no
row, and the first request on a fresh key deletes rows old enough to be full.

If you already limit `/sign-in/send-code` and `/sign-in/guest` at your edge,
set `rateLimit: false`; the guess bucket stays on regardless, because nothing in
front of this server can key on the address.

Scope is authentication abuse only — email flooding and code guessing. It is
not a general API limiter; that belongs in infrastructure in front of
everything, these routes included.

## OAuth

**State is verified** against a short-lived `HttpOnly` cookie scoped to the
callback path. Without it, an attacker hands a victim a callback URL carrying the
attacker's own authorization code and the victim's browser quietly completes a
sign-in as the attacker. The cookie is not signed, and does not need to be:
nothing in it is trusted on its own. The state has to match what the provider
echoed, the return path is validated, sign-up fields are checked against the
declared schema, the provider has to be this callback's, and a connect has to
be finished by the session that started it. Whoever can rewrite the cookie
already controls the browser it lives in. The payload carries when it was
issued, and a flow older than ten minutes is refused on the server's clock — the
cookie's own expiry is a browser courtesy, not the rule.

**PKCE on every exchange, and a nonce for Google.** The state cookie also holds
an S256 code verifier; only its challenge travels through the browser, and the
provider refuses to exchange an authorization code without the verifier — so a
code intercepted on the way back is worthless to whoever has it. Google's ID
token must additionally echo the nonce the authorize request carried, which ties
the token to this flow rather than to any flow.

**Google's ID token is verified, not decoded.** Signature against Google's
published keys, issuer, audience (your client id), and expiry — even though it
arrived over TLS from Google's own token endpoint. A provider outage, including
an unreachable key set, is reported as such rather than as a refused sign-in.

**Only verified email addresses are accepted.** GitHub returns unverified
addresses, so the library takes only the entry that is both `primary` and
`verified`; Google must report `email_verified: true`. Skipping this is a
complete account takeover, and row-level security cannot save you — it will
faithfully serve the attacker the victim's rows, because authorization cannot fix
an authentication failure.

**The redirect URI is derived per request** — from `X-Forwarded-Host` and
`X-Forwarded-Proto`, falling back to the request URL — unless `baseURL` pins it.
That is deliberate, and it is not the weak link people expect: a provider only
ever redirects to a URI registered in its own console, so a forged `Host`
produces an error page at GitHub or Google rather than an authorization code
delivered anywhere. The authorize request and the code exchange build the URI
from one function, so the two always agree — a mismatch is what providers reject.
Set `baseURL` when the canonical origin should be fixed regardless: a proxy that
rewrites the host without forwarding it, or a deployment answering on several
origins.

**Redirects are validated.** A `?redirect=` value must be a same-origin relative
path: it must start with `/`, and `//evil.example` is rejected because browsers
treat protocol-relative URLs as absolute.

**Connecting requires the same session** that started the flow. Otherwise an
attacker who lures a signed-in victim through a connect URL links their own
provider identity to the victim's account, and signs in as them afterwards. A
provider identity already linked elsewhere is never re-pointed.

## Sessions

The browser receives the refresh token only as an `HttpOnly`, `Secure`,
`SameSite=Lax` cookie with **no `Domain` attribute**, so it is never
broadcast to sibling subdomains. In production its name carries the `__Host-`
prefix, as does the OAuth state cookie: a browser accepts a `__Host-` cookie
only from the host itself, so a compromised sibling subdomain cannot plant one
and sign a visitor into an attacker's account. `Secure` — and with it the
prefix — is dropped in exactly one case: plain-HTTP `localhost`, where a browser
would refuse the cookie outright and local development would not work at all.
Every other origin gets it, including an endpoint called in-process where there
is no request URL to judge by. Narrowing `cookie.path` to the auth mount also
forgoes the prefix, which the browser allows only at `/`.

The token is `id.secret`, and the code is Lucia's `auth_session.ts` with the
database calls swapped in: thirty-two random bytes, base64 in the token,
SHA-256 in the row, compared in constant time. The id is whatever your store
names the row. Nothing stored says when a row dies: lifetimes are constants in
the library compared against the row's timestamps, as in Lucia and the
author's app, so changing `session.ttl` changes every live session at once. A leaked table yields nothing replayable, and the id can be
logged and shown in a device list because it proves nothing on its own. The cookie is not the
symmetric case: it *is* the credential. `HttpOnly` keeps script from reading it, but whatever does
obtain it — a stolen browser profile, a device backup, a proxy terminating
TLS — holds the session until that session is revoked or expires. Hashing
protects the database, not a stolen token.

Signing out reaches this device or every device, nothing in between. "Every
device but this one" is the scope a stolen session would use to lock the owner
out while keeping its own foothold; `global` costs the thief their session too,
and revoking one particular device sits behind identity verification. Revoking
the one this browser is on leaves a cookie pointing at nothing; the next
`/token` answers `null` and clears it, and `signOut` is the call that does both
at once.

**One cookie beside it is readable by script**, on purpose. `auth-ts.hint` holds
`in` or `out` and nothing else, and is written and retired with the refresh
cookie it shadows. It exists so a signed-out visitor costs no request: the
client reads it before asking `/token`, and a browser that has never signed in
skips the exchange entirely. It carries no credential and grants nothing —
whoever can read it can already see the signed-out page it produces. It is the
only cookie here that may carry a `Domain`, and only for a request from a
trusted origin on another host, because that app cannot otherwise see it.

**Every state-changing request must say `Sec-Fetch-Site: same-origin`.** CORS
headers decide who may *read* a response, not who may *send* a request: a
`POST` with a simple content type goes out without a preflight, cookie
attached. `SameSite=Lax` confines that to the same site, which still leaves a
sibling subdomain — or a browser that does not enforce it — able to sign the
user out, sign them into someone else's account, or have a guest's session
merged into an attacker's. So the check is the book's, as Lucia's
`auth_session.ts` has it: on every non-`GET` request the browser's own
`Sec-Fetch-Site` header must read `same-origin`. The browser sets it on every
request and forbids a page from touching it, so a cross-site page cannot forge
it, and a browser too old to send it is refused rather than trusted. Anything
else is **403 `forbiddenOrigin`** before the body is parsed.

The book's one fallback, for a sibling origin or an older browser, is an
`Origin` allowlist: a request whose header is not `same-origin` still passes
when its `Origin` is the server's own — as the runtime sees it, or as a proxy
forwarded it once `trustedProxyHeaders` is on — its `baseURL`, or one of its
`trustedOrigins`. A client that is not a browser sets the header itself, as the
`cookieStorage` client does: forgery is a browser attack, and there is no
browser there to protect.

**`X-Forwarded-Host` is read only when you say a proxy sets it.** Nothing about
a request distinguishes a forwarded header from one its sender wrote, and the
origin those headers name is both what the OAuth `redirect_uri` is built from
and an entry in the allowlist above — so reading them unasked would let a caller
nominate the origin it is then checked against. `trustedProxyHeaders` defaults
to `false`, and the origin is the request URL's own:

```ts
createAuth({
  // ...
  trustedProxyHeaders: true
})
```

Turn it on when this server sits behind a proxy that sets `X-Forwarded-Host` and
`X-Forwarded-Proto` and cannot be bypassed — a runtime that only ever sees an
internal URL, or an app answering on several approved domains. A `baseURL` wins
outright when set, so the two are alternatives rather than layers: pin the origin
or derive it, not both.

**Request bodies must be `application/json`**, with `utf-8` as the only
charset a parameter may name, or the answer is **415 `unsupportedMediaType`** —
the author's check. This is the second, independent layer: a page cannot send
that content type cross-origin without a preflight, so a browser stops most of
these before any header reaches the server. That is a bonus and not the
guarantee — whoever answers the preflight is your application's business — so
the check runs on every request regardless. The client already sends it;
bodiless requests such as `GET /users` are untouched. A body over 16 KiB is
**413 `payloadTooLarge`** before it is parsed — the cap the author's server
puts on every request — refused by `Content-Length` where there is one and
otherwise the moment the stream passes it. Header sizes and read timeouts are
your runtime's to set.

**`GET /token` is the one route a cookie alone authenticates**, and being a
bodiless `GET` it is exempt from both layers above. That is safe for the reason
CORS exists: a cross-site page can *send* the request, but without an allowed
origin the browser will not let it *read* the reply, which is where the token is.
Every other authenticated route takes the bearer and nothing else, so a request
carrying only a cookie cannot act for anyone — the whole class of cross-site
request forgery ends at that one route.

With no session it answers **200 with `null`**, not 401, and expires whatever
dead cookies the request presented on the way out. Nobody signed in is the
answer to the question, not a failure to answer it; and only an answer can carry
`Set-Cookie`, which is what stops the next page load asking again.

## Accounts

`type` is written by core only as `guest` or `user`, and only on insert — so
signing in cannot demote an administrator, and no endpoint can produce `admin`.
`POST /user` rejects `email`, `phoneNumber`, and `type`.

Additional fields are an allowlist applied on insert only. On an existing user
they are ignored, because otherwise any sign-in request could rewrite profile
columns.

Revoking another device and deleting the account both need a verified
identity: a code from `/user/verify/send-code`, checked by `/user/verify`. What
that leaves behind is filed under the session that asked and bound to the
browser holding the attempt cookie, lasts an hour, and is not spent by the
actions it allows. No other session of the same user can use it, and there is
no "signed in recently enough" bypass — a hijacked session is exactly the one
that is recent. The challenge answers **403 `verificationRequired`**, never a
2xx, so a client cannot mistake it for success and tell someone their account
is gone when it is not.

Signing out this device, or every device, needs nothing: a hijacker who does
either signs themselves out too.

Codes carry a purpose. A sign-in code cannot confirm an identity, and an
identity code cannot sign anyone in.

## In the browser

The book's storage chapter says the choice between cookies and Web Storage
matters less than what an XSS can reach, so here is what the client keeps and
where:

| what | where | readable by script? |
| --- | --- | --- |
| refresh token (the session) | `HttpOnly` cookie, `__Host-` prefixed in production | no |
| access token | a variable in the client, in memory | yes, by the page's own code |
| the signed-in user | the same variable | yes |
| sign-in hint (`in`/`out`) | `auth-ts.hint` cookie | yes, by design |

The access token is never written to `localStorage` or `sessionStorage`: in
memory it dies with the page, whereas a persisted bearer token turns any script
injection into a credential that keeps working after the tab is closed. What a
script injected into your page *can* do is call the auth endpoints as the user,
same as the book notes for `HttpOnly` cookies — the attribute stops export, not
use. That is why the destructive actions sit behind a fresh identity check:
revoking a device, deleting the account and, later, changing the address need a
code from the inbox, which a script does not have.

**A Content Security Policy is yours to set**, from wherever your framework
sets headers, and it is the defence the book asks for against XSS. The author's
app ships one on every page:

```
default-src 'none'; script-src <hash>; base-uri 'none'; img-src <your images>;
connect-src 'self'; style-src <hash>; frame-ancestors 'none'; form-action 'none';
```

`connect-src 'self'` is enough for this library on a same-origin mount; a
cross-origin auth server needs its origin listed there. Nothing here needs
`unsafe-inline` or `unsafe-eval`.

**No personal data is kept on the client** beyond the user object your page
asked for, and the book's rule applies to whatever you add: neither cookies nor
Web Storage encrypt anything, so nothing sensitive belongs in either.

## Cross-origin

When the application and the auth server share an origin — the usual case, and
what the reference application does — there is nothing to configure here.

When they do not, name the application:

```ts
createAuth({
  // ...
  trustedOrigins: ["https://app.example.com"]
})
```

That grants trust: an origin listed there may make state-changing requests, and
is the one whose host the sign-in hint can be scoped to. It sends no CORS
headers.

**CORS is yours.** This library does not set `Access-Control-*` on any response
and does not answer `OPTIONS`. That is deliberate: an application with one CORS
policy across its API should not have to carve an exception out of it for this
mount, and two things both claiming to own the policy is worse than either
owning it. Configure it wherever you already do.

<Callout type="warn">
  Whatever answers the preflight has to allow credentials, or the browser
  withholds the session cookie and `GET /token` answers `null` however the
  server is configured. It also has to allow the `authorization` and
  `content-type` headers, or every authenticated route fails its preflight.
</Callout>

On TanStack Start, the auth mount is an ordinary server route, so CORS goes in
`src/start.ts` alongside anything else that wraps a request:

```ts title="src/start.ts"
import { createMiddleware, createStart } from "@tanstack/react-start"

const ALLOWED = new Set(["https://app.example.com"])

export const startInstance = createStart(() => ({
  requestMiddleware: [
    createMiddleware().server(async ({ next, request }) => {
      const origin = request.headers.get("origin")
      const allowed = origin && ALLOWED.has(origin)

      if (request.method === "OPTIONS" && allowed) {
        return new Response(null, {
          status: 204,
          headers: {
            "access-control-allow-origin": origin,
            "access-control-allow-credentials": "true",
            "access-control-allow-methods": "GET, POST, DELETE, OPTIONS",
            "access-control-allow-headers": "content-type, authorization",
            "access-control-max-age": "600"
          }
        })
      }

      const result = await next()
      if (allowed) {
        result.response.headers.set("access-control-allow-origin", origin)
        result.response.headers.set("access-control-allow-credentials", "true")
        result.response.headers.append("vary", "origin")
      }
      return result
    })
  ]
}))
```

Echo the origin rather than sending `*`: a wildcard is refused by browsers
alongside `Allow-Credentials`, correctly, since it would let any site read a
credentialed response.

<Callout>
  Vite answers preflights itself in `dev` and `preview`, permissively for any
  localhost origin and without `Allow-Credentials`. That shadows whatever you
  write, so set `server.cors` and `preview.cors` to `false` and let your own
  handling run in every environment.
</Callout>

## Deploying

The client's IP address needs no configuration to work: `x-forwarded-for` is
read, and a header carrying a single entry is taken as the client. That is
correct on any platform whose proxy overwrites the header rather than appending
to it, which is most of them.

What is never trusted is a chain nobody vouched for. Proxies *append*, and the
header starts as whatever the client typed — so with two or more entries and no
declared topology, none of them is used, and the per-IP limits sit out that
request rather than keying on an address the caller chose. Two ways to make a
chain readable, both under `ipAddress`:

- `trustedProxies: 1` — the number of proxies you run. The client is that many
  hops from the right. Use this where proxy addresses are not enumerable, which
  includes Cloudflare and Vercel.
- `trustedProxies: ["10.0.0.0/24"]` — their addresses or ranges, when you run
  them yourself. The chain is walked right to left, your hops are skipped, and
  the first entry that is not yours is the client.

Stronger than either: point `headers` at a single-value header your platform
sets and a client cannot append to — `cf-connecting-ip` on Cloudflare,
`true-client-ip` on Akamai, `x-real-ip` on Railway and behind nginx, which is
the one the book's author reads. Neither form verifies who actually connected, only
how the header is read, so keep the app reachable only through those proxies.

Whatever arrives is validated as an IP address before it becomes a rate-limit
key or a stored column, and normalized first, so `2001:DB8::1`,
`2001:db8:0:0:0:0:0:1`, and `::ffff:203.0.113.7` cannot buy a caller three
buckets for two addresses. IPv6 limits count per `/64` — a residential client
owns the whole prefix, so per-address counters would be rotated past for free.

When no address can be derived at all, the per-IP limits do not apply and
nothing is written to `session.ipAddress`; the per-address guess limit is
unaffected, and the first request it happens to says so in your logs. Requests are never merged into one shared bucket in that case, which
would let a single caller lock everyone out of a flow.

If your database exposes a REST API, check what it grants by default. Neon, for
example, grants the `authenticated` role full access to everything in `public`
when the Data API is enabled — so the auth tables must be explicitly protected,
or any signed-in user can read every code in your system.

The split is per table:

> `users`, `sessions`, and `identities` are yours to query.
> `verifications`, `rateLimits`, and `identitySecrets` are never granted.

Nothing in the first three can authenticate anybody, so reading them whole is
safe. The second three hold a credential or the identifier somebody is signing
in with, and they are protected by having no policy rather than by a column
grant — forgetting a policy leaks nothing, where forgetting a revoke leaks
a credential. See [the Neon guide](/docs/guides/neon) for the SQL.
